# AI services

This directory contains the AI workloads that ship with the papAIa Lean Core.
Each service has its own subdirectory with a `docker-compose.yml`, an
`.env.example` and any service-specific config files.

For the architecture overview and the OIDC integration model, see the
[top-level README](../../README.md). For Compose-level orchestration — profiles,
bind mounts, inspecting a running stack — see [`src/README.md`](../README.md).

---

## How these services fit together

```
LibreChat  ──▶  LiteLLM  ──▶  LocalAI / hosted providers
   │                 ▲
   │ MCP tools       └── Jina reranker (rerank endpoint)
   ▼
mcp-firecrawl  ──▶  Firecrawl        (../services/firecrawl)
add-on MCP servers ──▶ their own apps (separate repos, own networks)
```

- **LibreChat** is the user-facing chat UI. It authenticates with Keycloak
  (native OIDC, PKCE), routes model calls through LiteLLM, and consumes MCP
  tools listed in the rendered `librechat.yaml`.
- **LiteLLM** unifies access to local and hosted LLMs and is the single egress
  point for anything that leaves the host.
- **LocalAI** runs chat-completions inference locally (CPU or NVIDIA GPU).
- **mcp-firecrawl** exposes Firecrawl's crawl / scrape / search / map / extract
  capabilities as MCP tools.
- **Jina reranker** is an optional reranking endpoint in front of LiteLLM.

Everything beyond that — document management, RAG, workflow automation — is an
add-on. An add-on brings its own MCP server on its own network and contributes
an `mcpServers` fragment to `librechat.yaml` at render time; nothing in this
directory changes when one is installed. See
[Add-ons](../../README.md#add-ons).

## Configuration

Per-service configuration lives in each subdirectory's `.env`, generated by
`tools/papaia-ctl setup` from the shipped `.env.example` and kept in sync
across services — a Keycloak client secret and the consuming service's
`OPENID_CLIENT_SECRET` / `GENERIC_CLIENT_SECRET` are generated once and fanned
out. Nothing here has to be filled in by hand.

The canonical copy of every `.env` lives under `$PAPAIA_CONFIG_DIR`; the files
inside the checkout are derived copies overwritten on every `start`. The full
variable reference is in [`docs/configuration.md`](../../docs/configuration.md).

## Services

### LibreChat — multi-provider chat UI

- Profile: `librechat`
- Image: `ghcr.io/danny-avila/librechat`
- External port: `8000`
- Auth: native Keycloak OIDC, PKCE enforced
- Sidecars: MongoDB, Meilisearch, pgvector, RAG API
- Configuration: `librechat.yaml` (model & MCP definitions, rendered into
  `$PAPAIA_CONFIG_DIR/ai/librechat/`) plus `.env`

### LiteLLM — LLM proxy and gateway

- Profile: `litellm`
- Image: `ghcr.io/berriai/litellm`
- External port: `8200` (proxy + admin UI)
- Auth: generic OIDC for the admin UI, master key for programmatic clients
- Sidecars: PostgreSQL, Prometheus (internal only)
- Configuration: `config.yaml` (provider routes), `prometheus.yml`, `.env`

### LocalAI — local chat-completions inference

- Profile: `localai`
- Image: `localai/localai` (CPU) or its NVIDIA CUDA variant
- External port: `8080`
- Auth: native OIDC, gated by the `localai-access` realm role
- The models to download are listed in `localai/models.txt`; per-model YAML
  lives next to it in `localai/models/`. Both are render targets, so an
  `overlay/` copy survives every upgrade.

### mcp-firecrawl — Firecrawl MCP bridge

- Profile: `librechat-websearch`
- Image: `ghcr.io/firecrawl/firecrawl-mcp-server` (digest-pinned)
- No published port: reachable only from `papaia-net`, which is the security
  boundary — the server itself does no authentication.
- Talks to the Firecrawl service in
  [`../services/firecrawl/`](../services/firecrawl/) via `FIRECRAWL_API_URL`.

### Jina reranker (optional)

- Profile: `librechat-websearch`
- Image: `ghcr.io/fidonis/jina-reranker-api`
- No published port; called by LiteLLM over `papaia-net`.
- The model is chosen at setup time (`--reranker-model=NAME`) and reaches the
  container as `RERANKER_MODEL`.

## Adding a new AI service

Prefer an **add-on** for anything application-specific: it lives in its own
repository, declares its integration points in `papaia-app.yaml`, and needs no
change to any tracked file here. See
[Add-ons](../../README.md#add-ons) and
[`docs/architecture.md`](../../docs/architecture.md).

Add a service to this directory only when it belongs to the Core itself:

1. Create `src/ai/<your-service>/` with a `docker-compose.yml` that joins
   `papaia-net`, pins its image tag inline, and declares a `profiles:` entry.
2. Add a `.env.example` documenting every variable the compose file
   interpolates — including those with an inline `:-` default.
3. If the service speaks OIDC, register a client in
   `src/infra/keycloak/realm-import/papaia-realm.json.template`, add a
   `KC_<service>_CLIENT_SECRET` to `src/infra/keycloak/.env.example`, and wire
   the alias in `SECRET_ALIASES` (`tools/lib/secrets.py`) so setup fans the
   value out.
4. If it does not, route it through oauth2-proxy — see
   [`../infra/keycloak/README.md`](../infra/keycloak/README.md) for the NPM
   snippet.
5. Add an `- path: ./ai/<your-service>/docker-compose.yml` entry to
   `src/docker-compose.yml`.
6. Document the image in [`THIRD_PARTY_LICENSES.md`](../../THIRD_PARTY_LICENSES.md)
   — CI fails otherwise — and add the service to this README and to the profile
   table in [`src/README.md`](../README.md).
