# 0004. Offer the RAG system as an optional core profile instead of three add-ons

## Context

Until 0.8.0 the RAG services (Qdrant with an MCP server, and a WebDAV ingester)
were part of the core. Release 1.0.0 removed them (#92) to keep the core to what
every instance needs as a generic platform, and RAG became a Tier-2 add-on. It
exists today as three catalogue add-ons in `Fidonis/papaia-addons`: `qdrant`
(Qdrant plus `qdrant-mcp-rbac`), `qdrant-connect` (the MCP server against an
existing Qdrant) and `qdrant-ingest` (the ingester with its web interface).

Running RAG through the add-on contract has proved awkward, because the contract
cannot express what the pieces need:

- `papaia-ctl setup` cannot ask about an add-on. Its public URLs, such as the one
  of the ingest web interface, are set by hand afterwards.
- The Keycloak clients, the audience mappers on the `librechat` client and the
  realm roles are printed as a checklist and imported by hand.
- The LiteLLM master key is copied by hand into two `.env` files, and the shared
  Qdrant secret is entered by hand in the ingester.
- An add-on cannot attach to another add-on, so the ingester reaches Qdrant over
  `host.docker.internal` and a published port.
- `papaia-manager` has no way to learn that the services exist, so it shows no
  tile for them.

Two properties of the platform make a core module the better fit now. The core
already has an established way to carry an optional component, as `localai` and
`manager` show: a Compose profile chosen during setup, with its realm client,
secret fan-out and URL kept in the core. And RAG is a capability that most
installations either want or explicitly do not, rather than an application that
attaches to the platform.

## Decision

- The RAG system returns to the core as the **optional Compose profile `rag`**
  (`src/ai/rag/`, module label `papaia-rag`). It is off by default, so a stack
  without it is unchanged and the lean-core premise holds.
- The profile holds four services on `papaia-net`: `qdrant` (JWT RBAC enabled),
  `qdrant-mcp` (`qdrant-mcp-rbac`), `qdrant-ingest` and `qdrant-ingest-tika`.
  LibreChat reaches the two MCP endpoints by service name. Only the Qdrant REST
  port and the ingest port are published.
- `papaia-ctl setup` asks one yes/no question and, on "yes", for the browser URLs
  of Qdrant and of the ingest web interface, with suggested values like the other
  services. `QDRANT_PUBLIC_URL` and `QDRANT_INGEST_PUBLIC_URL` are derived and
  stored whether or not the profile is on, so a later opt-in keeps them.
- The Keycloak objects belong to the core realm template: the bearer-only clients
  `mcp-qdrant` and `mcp-qdrant-ingest`, the confidential client
  `qdrant-ingest-ui`, the audience mappers on `librechat`, and the realm roles
  `qdrant-admin` and `qdrant-ingest-operator`. Following ADR 0003, both roles are
  composites of `papaia-admin`.
- An existing realm is not re-imported, so `keycloak_role_sync` creates the three
  clients while the profile is active (`PROFILE_CLIENTS`). For a client that
  already exists, for instance one left over from the add-on, it sets the secret
  to the value in the core `.env`, which is canonical, and changes nothing else.
  It does nothing when the profile is off. This makes `setup` with the RAG
  option, followed by `start`, work on an installed stack.
- The secrets are generated by setup. The LiteLLM master key and the Keycloak
  client secret reach the module through `SECRET_ALIASES`.
- The LibreChat MCP entries are a core fragment (`src/ai/rag/integration/`) that
  `render_core` merges only while the profile is active (`PROFILE_FRAGMENTS`), so
  a stack without RAG lists neither server.
- The core does not retire the three add-ons. Both forms cannot run on one host,
  since ports 6333 and 8300 and the service names `qdrant-mcp` and `qdrant-ingest`
  would collide, so `setup` refuses to enable the profile while one of them is
  active. Removing them from the catalogue is a separate change.
- This module is not LibreChat's built-in file search. `librechat-ragapi` and
  `librechat-vectordb` stay in the `librechat` profile, and both can run together.

## Consequences

- **Positive**: one setup answer replaces the hand wiring. Keycloak clients and
  roles, the secrets and the MCP registration come with the profile, on fresh
  and on existing installations. `status`, `doctor`, backup and restore handle the
  module through the compose inventory without a list to maintain, and
  `papaia-manager` can show tiles and a menu category for it.
- **Negative**: the core grows by four services and a set of realm entries, which
  every installation carries in its realm whether or not it enables the profile.
  The core also takes on the update cadence of Qdrant, `qdrant-mcp-rbac`,
  `qdrant-ingest` and Tika, and the architecture document's roadmap entry that
  planned to migrate the RAG bundle into the catalogue no longer holds for it.
- **Neutral**: the core ships no models, so an embedding model has to be added to
  LiteLLM before the first ingest run. The ingester stores the Qdrant API key
  encrypted and rejects a plain value, so the connection to `http://qdrant:6333`
  is added once in its web interface.

## Alternatives considered

- **Keep RAG as add-ons and improve their installer** — rejected: the add-on
  contract has no way to ask a setup question, create Keycloak clients or register
  a manager tile, and those are exactly the missing pieces.
- **Enable RAG by default** — rejected: the stack grows heavier and the services
  need an embedding model that the core does not ship.
- **One compose file per service with its own profile** — rejected: the pieces
  depend on each other (shared secret, audience, ingest reaches Qdrant), and a
  single `rag` switch matches what an operator decides.
