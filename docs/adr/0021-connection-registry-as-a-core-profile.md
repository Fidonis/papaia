# 0021. Ship the connection registry as the optional core profile connections

## Context

Modules reach mail servers, calendars, databases and other targets on behalf of a person
or a team. Each of them could keep its own copy of the account and its password; then
the same credential lives in several stores with several rules, and a person cannot see
which module used it. The repository `papaia-connections` holds the one store for saved
credentials: an administrator approves targets, a person adds an account once, and a
module gets the credential only sealed to a key valid for one call, with every use in the
registry's journal and in the audit log.

Add-on contract generation 9 already names the registry: an add-on may list
`connections` under `networks.attach`. Me, Flow and the assistant name it as a neighbour.
Until now the core did not ship the service, so the generation promised something no
installation could provide.

The registry keeps credentials. Its database login must not be able to change the journal
or its triggers, its master key must not be readable by any other container, and a
restored database is worth nothing without the keys that open it.

## Decision

1. **One optional core profile `connections`** in `src/infra/connections/` with three
   services of the module `papaia-connections`, all from pinned images
   (`name:tag@sha256:<digest>`):
   - `connections`, the registry, on `https://connections:8080`;
   - `connections-migrate`, a one-shot container that applies the migrations;
   - `connections-db`, PostgreSQL.
   `papaia-ctl setup --connections` switches it on; it is off on a fresh install.
2. **Two database logins.** Only `connections-migrate` holds the owner of the schema
   (`connections_owner`). The registry connects as `connections_service`, created on an
   empty database by an init script without further attributes; the migration grants it
   data rights only. The registry refuses to start with the owner's login or with the
   owner's URL in its environment. Both passwords are generated by `setup` and handed to
   the database as secret files.
3. **Reachable by its declared consumers only.** The registry is on
   `papaia-connections-net` with `me-web`, and on the network of every add-on that attaches
   `connections` (Flow's `flow-control`, the assistant's `assist-gate`). It is not on
   `papaia-net`. The database and the init container are on the internal
   `papaia-connections-db-net`; no add-on may attach either of them
   (`compat.NEVER_ATTACHABLE`). `papaia-connections-net` is not internal: the registry
   reads the signing keys of the public issuer through the host.
4. **Mutual TLS.** The registry serves TLS 1.3 with a server certificate of the platform
   PKI (`src/infra/connections/pki.yaml`, ADR 0019) and asks every caller for a client
   certificate of the platform CA. An operator may clear `CONNECTIONS_TLS_CLIENT_CA` to
   allow one-sided TLS; the profile `kritis` refuses that. Audit rows go to
   `papaia-audit` as the source `papaia-connections` with a certificate of the audit
   ingest CA.
5. **Keys stay with the registry.** The volume `connections-keys` is mounted into the
   registry and into no other container. `papaia-ctl backup` archives it with
   `connections-db`, both encrypted to the operator's recipients like every other
   archive, and both under the module `connections`, so `restore --only=module:connections`
   brings them back together.
6. **Identity.** While the profile is on, the realm sync reads the profile's
   `exposes.yaml` like an add-on's declaration: it keeps the realm role
   `connections-admin` (part of `papaia-admin`) and the bearer-only client
   `papaia-connections`, the registry's audience. Without the profile none of them is
   created. The kit's naming register does not list `connections-admin` yet; the core
   adds it to its snapshot until it does (`realm_sync.PROFILE_ENTRIES`).
7. **Catalog and suite.** The catalog lists the registry from the profile's
   `exposes.yaml`, a copy of the module's own declaration; the suite matrix names
   `papaia-connections`. The copy differs from the module's own in two places:
   `scheme: https`, and an `id_field` on the resource of the two operations that create
   an object, since the platform catalog needs one with every resource.
8. **Key change.** `papaia-ctl secrets rotate connections/credentials` runs the registry's
   `rotate-keys` in the running container: a new master key becomes active and every
   stored credential is sealed again. One `papaia.audit/1` row records the outcome.

## Consequences

- **Positive**: generation 9 is true: an add-on that attaches `connections` finds the
  registry, and no module needs a credential store of its own.
- **Positive**: the running registry cannot change its schema, and its keys are in one
  container and one encrypted backup archive.
- **Negative**: a caller needs a client certificate of the platform CA; `me-web` does not
  present one yet, so its calls need `CONNECTIONS_TLS_CLIENT_CA` cleared or a client
  certificate added to Me.
- **Negative**: the pinned image is a candidate build until the module is released; the
  pin is moved to the published digest then.
- **Neutral**: switching the profile off keeps the realm's role and client; they are
  removed like those of an uninstalled add-on only through the uninstall journal.

## Alternatives considered

- **An add-on bundle of the registry.** Rejected: several modules depend on it, Me shows
  it, and the add-on contract already treats it as a core service (generation 9).
- **The registry on `papaia-net`.** Rejected: every service of the stack could reach it.
- **One database login for migrations and service.** Rejected: the service could alter
  or drop the journal's triggers.
- **Key volume outside the backup.** Rejected for the default key files: a restored
  database could not be read. For critical infrastructure, `kritis` refuses key files and
  keeps the master key in OpenBao or a hardware security module instead.
